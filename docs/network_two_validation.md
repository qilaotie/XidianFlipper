# COM9 / COM10 双机网络消息验收

日期：2026-10-27。两台均运行应用 SHA-256 `c2f01fe6271b5301754974cfa3bfd953eac038a8f11068dc63845df871d16739`，ESP-IDF 5.5.4 / ESP32-C6，2 MiB 单应用分区。本轮没有为测试改变固件或注入协议包、好友、消息、分数或存档。

## COM10 安全更新

COM10 最初是旧三槽分区，普通应用更新工具在写入前拒绝。用户明确同意后，迁移工具对整片 4 MiB Flash 新鲜双读、校验磁盘备份，依次写应用、OTA 选择区和最后的分区表。整片回读确认允许写入范围外字节完全不变，包括 NVS / nvs_sec；原 bootloader 与发行版相同，没有替换。私有备份和迁移记录位于忽略的 `build/migration-private/pre-migrate-20261027T052742Z/`，不得上传。

## 实机结果

采用 COM10 发、COM9 收，避免已满的 COM10 收件箱因测试淘汰旧消息。设备原本互为好友，测试没有重新配对或删除好友。

| 场景 | 实际操作与证据 | 结果 |
| --- | --- | --- |
| 邻居发现 | 两台同频道开启 MESH，界面显示各一个直连节点 | 通过 |
| 同频道群聊 | 频道 1 发送 QG01，COM9 画面与持久收件箱均出现该正文 | 通过，保存一次 |
| 频道隔离 | COM9 改频道 2，COM10 在频道 1 发 QG02 | COM9 未接收或入箱该消息 |
| 全网公告 | 维持不同频道，COM10 发 QA01 | COM9 收到 `[ALL] QA01`，频道 0，保存一次 |
| 关闭网络排队 | COM10 在 MESH OFF 时确认给 COM9 排队 QO01 | 持久 WAIT，尝试数 0，没有投递 |
| 目标离线 | 只读方式把 COM9 保持在 ROM/stub 下载状态，应用和无线程序不运行；COM10 开启 MESH | 发射尝试后仍为 WAIT，没有假报 DELIVERED |
| 重启后继续 | 发送端通过正常硬复位重新启动，留言仍保留旧会话/消息编号 | 通过 |
| 恢复目标与回执 | 恢复 COM9 正常运行，两台开启 MESH 等待投递 | COM9 保存 QO01 一次，COM10 持久状态 DELIVERED（本次 3 次尝试） |

测试均通过真实设备的旋钮/短按/返回等价 USB 输入操作，发送需要显式确认。只读 Flash 检查使用 SDK 的 NVS 解析器核验条目/数据 CRC，并逐项比对：目标设备、原始会话/消息编号、收到的测试正文、持久送达状态，而不是只看屏幕“已发出”。这不是两个虚拟节点或主机转发消息。

## 清理与保留

- 两台频道均恢复到原来的频道 1，网络开关随正常重启恢复 OFF，最终回首页。
- COM10 的测试工作草稿清空，恢复原本空草稿；测试发件箱任务移除，没有留下持续重试。
- 两台已有六槽保存草稿、好友记录和原收件箱记录均逐项校验保留。COM9 原收件箱 18 条，测试后 21 条；COM10 原来与测试后都是 32 条，没有淘汰旧消息。
- COM9 保留 QG01、`[ALL] QA01`、QO01 三条测试消息，方便用户自行查看。没有操作宠物、游戏或商店。
- 私有原始 NVS、状态 JSON、日志和截图留在忽略的 `build/network-two-private/`，不发布。工具代码见 `inspect_message_nvs.py`、`smoke_network_two.py`、`verify_network_two.py`。

## 不能据此声称的结果

本轮只有两台物理设备，验证的是直连收发、频道隔离、公告接收、离线排队及目标回执闭环。**没有验证 A→B→C 第三台中继**、大规模广播全员送达、任意距离网络、长时间拥塞或突然掉电故障。把目标停在 ROM 后恢复可验证真实无线离线，不等于做了电源拔插或 NVS 写入中断测试。

三台隔离直连的实验仍按 [自组网说明](local_mesh.md) 进行。当前没有加密或管理员认证，公告也不是可靠应急通信。
