# 离线留言、全网公告与多跳群聊

2026-10-27 本地实验源码。基于[多跳自组网](local_mesh.md)，不使用互联网或路由器。网络操作和状态已补齐中文，跟随设置中的语言开关；下文保留英文项名方便对照。

## 入口与写消息

消息菜单末尾增加：

| 入口 | 用途 |
| --- | --- |
| Mesh group chat | 向当前频道发送多跳群聊文字 |
| Network announcement | 跨频道发送公告 |
| Offline message | 给已经配对的好友排队留言 |
| Offline outbox | 查看六个离线留言槽位、手动重试或取消删除 |

前三项先进入操作页：第一行 `Edit` 打开已有编辑器，可继续当前草稿、从草稿箱加载或插入表情；在编辑器组选单按 BACK 保存并回操作页。第二行进入确认流程，第三行打开网络开关，第四行打开离线发件箱。预览文字不会发送。

确认页默认停在 Cancel，转到最末一行才执行。留言先选择好友再确认；不会把频道广播自动变成离线私信。普通 SEND 仍使用原有即时发送流程，不会偷偷增加持久队列。

## 多跳群聊

参与中继的同版设备先在 `工具 → Local mesh network` 开启 MESH，聊天双方选择相同频道 1–16；操作页会显示发送频道，确认时使用当时的频道。

消息沿附近开启中继的同频道节点传播，最多三条无线链路。没有邀请制成员列表、密码房间、在线成员确认或历史消息补齐。离开覆盖范围后收不到的群消息不会由本版自动补发。收件箱保留本机实际接收的消息。

`Sent` 仅表示本机广播完成，不表示每个群成员收到。不为广播制造“全部已读/全部送达”计数。网络 OFF 时显式群聊操作拒绝发送并提示；普通即时消息的直连入口仍保留。

## 全网公告

公告允许跨频道传播，但“全网”只指**开启 MESH、同版且在最多三跳无线覆盖内的设备**，不是整个校园、互联网或无限距离网络。关闭网络的节点不接收这类公告。任何开启网络的同版节点都可以发起，没有管理员身份认证。

用户正文最多 122 个可打印字符，发送前增加 `[ALL] `，总长度不超过原有 128 字节。收件箱以普通文字格式保存，查看时标注 ALL；标记只是展示信息，不证明来源权威。公告不要求每台节点回执，也不保证全部覆盖。

协议使用原 v3 保留 flag 位 `0x10` 标识公告，只允许 ROUTED 的 QUICK 广播、频道 0，禁止定向公告和公告 ACK 请求。所有节点都要更新；上轮中继固件和原直连固件不认识公告标志。包长度、消息入箱结构和 NVS 全局版本未改。

## 离线留言与发件箱

- 发送方本机有 6 个持久槽，正文最多 128 个可打印 ASCII 字符，只能发给已配对好友。它与六槽草稿箱不同：草稿是可编辑模板，发件箱是已经确认的投递任务。
- 先成功写入独立 `msg_outbox/outbox_v1` 才显示排队成功。网络关闭、好友离线或设备暂不可达时保留任务；不自动淘汰旧记录，即使已送达也由用户删除后才能腾位置。
- 开启 MESH 后低优先级轮询投递：单条尝试间隔至少 30 秒，所有槽合计至多每 10 秒开始一次尝试；六槽轮流，不让前面的任务一直占用机会。本地即时文字、控制包和实时摩斯优先。
- 每条最多 120 次投递尝试，预算在发射前持久保存。达到上限显示 HELD，保留正文，用户可 `Retry now` 重新启动预算。收件好友已删除或设备身份不符时也会暂停为 HELD。
- 重启保留消息、原始会话/消息编号和尝试预算；重启后 MESH 仍默认 OFF，需重新开启才能继续，启动约 30 秒后才开始恢复尝试。没有可靠实时时钟，因此不声称按自然日到期。
- WAIT 表示仍在等待目标回执。只有原目标好友、原会话和消息编号都匹配，且“已送达”状态写入成功，才显示 DELIVERED。经过中继发出或中继听到了都不算送达。
- 接收端仍须先保存进收件箱再回执。回执丢失会继续重试；在现有收件箱/去重窗口内避免重复入箱，但不承诺记录被淘汰后或无限时间跨度内的严格 exactly-once。
- `Delete / cancel` 二次确认后移除本机任务，不再安排后续尝试；已经开始广播的数据无法撤回，目标已收到的消息也不会被远程删除。
- 本版是**发送设备保存、以后再次尝试投递**，不是其他中继替你长期缓存。发送设备关机时不会由网络代投；排队不等于保证送达。

## 隐私与兼容

没有新增加密、认证或管理员签名。群聊、公告、好友留言仍可能被附近设备监听、伪造或重放；CRC 不提供安全保证。不要发送密码和敏感内容，不能当作应急通信。草稿、发件箱、收件箱均不上传云端。

NVS 采用独立命名空间，原 NVS v7/storage ABI 1、宠物、草稿及分区不改。读取未知版本或损坏记录时停止写入该发件箱，不静默清空；写入失败不会误报已排队或已送达。恢复出厂仍会清除本机数据。

## 验证范围

10 月 27 日后续已完成[COM9 / COM10 双机验收](network_two_validation.md)：真实同频道群聊、频道隔离、跨频道公告、接收端停机等待、发送端重启保留、接收端恢复后投递与持久目标回执均通过。两台的旧收件箱/好友/保存草稿保留，测试发件箱已清理。此结果仍不等于三台设备的中继射频验证。下面的单机记录是先前阶段，不作为本轮全部结果。

主机测试：`test_message_outbox.py` 覆盖六槽持久化、重启稳定编号、公平调度、失败写入/回执、120 次暂停、取消和损坏记录保护；`test_mesh_route.c` 覆盖公告跨频道/群聊隔离及三跳；`test_network_messages.py` 执行生产接收逻辑，检查入箱后回执、公告接收开关及目标回执持久化；`test_network_actions_ui.py` 检查预览/取消不发送、显式确认和失败保护。

这些不等于真实多设备射频验收。至少用三台同版设备验证隔离 A-C 的 B 中继、跨频道公告、不同频道群聊隔离，以及 C 离线后恢复时留言收到并回执。COM9 单机只能验页面和本机状态。

本轮构建应用 1,597,504 字节，2 MiB 槽剩 499,648 字节；ESP-IDF 5.5.4 构建和源码清单核验通过。用户接回 COM9 后，已完成应用更新、完整回读及分区/两处 NVS 不变核验。`tools/smoke_network_messages.py` 实机通过三项入口、网络设置往返、六槽状态与删除取消检查，最后回首页，无重启或断言。测试没有发送消息、创建排队任务或更改用户草稿；这不是多设备投递或真实掉电故障测试。证据只留在忽略的 `build/network-messages-smoke/`，不上传私有记录。
